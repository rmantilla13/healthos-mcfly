# healthOS for iPhone

The healthOS dashboard as a native SwiftUI app. It also sends your iPhone's Apple Health data to the server automatically, so you don't need the manual `export.zip` import.

## Dashboard

The app reads the same API as the website (`/api/summary`, `/api/trends`, `/api/workouts`, `/api/status`). It shows the same numbers, including WHOOP recovery and strain, which only the server has.

**Layout:** the web's phone layout (`src/components/shell/MobileNav.tsx`), in `Shell/`.
- **Tabs:** Home, Vitals, Body, Nutrition and More. Each tab keeps its own pages pushed over it.
- **More** lists the rest, in the web's order: Family (signed in on a server with accounts, while you share), Cycle (while cycle tracking is on), Journal, Sleep, Blood records, Ask McFly, Profile and Integrations, then Insights, which only the iPhone has. Signed out, the sign-in screen covers Home with no tab bar, and its **Change server** is the way to More: it opens Profile there, for the server address, and from there More's other pages ask for sign-in.
- **Your avatar** at the top right of every page (in Home's header, which hides the bar) opens the account menu, "Your workspace", as the web's phone shows it: a sheet from the bottom on the pale green menu gradient, as tall as its rows, in DM Sans with sage icons (the system's menu can't take the app's font). Profile, Integrations, Privacy & data (the server's `privacy.html`, shown in the app), Admin for admins (the web dashboard's Admin page, shown in the app, where it asks for sign-in again), and Sign out (in the quiet grey) while signed in on a server with sign-in. The shell opens what was chosen once the menu has gone.
- **Pages by the web's ids** (`AppRoute`): every button, card, insight, pattern and flag opens its page with `dashboard.open(_:)`, where the web's phone layout has it. A tab's page opens on its tab, at its top; one day by hour opens over Home; everything else is pushed under More. The web's old addresses still work: `settings` is Profile and `activity` is Body's Activity tab. Links carry the web's query (`body?tab=activity`, `family?member=<id>`, `profile?connect=openai`). The app's own text links are `healthos://<page>?<query>`; no URL scheme is registered, so only the app's text opens them.
- **`dashboard.tab = .settings`** (Open Profile, Change server, the hidden-cards note) opens Profile under More, as the web's `#/settings` does.
- **Nothing outlives what it showed:** a session that ends without Sign out (a 401), the server unreachable or another server, every pushed page goes except Profile. Sign out goes back to Home with nothing pushed on any tab. A tab whose pages are taken away like this has its navigation built again from nothing. A page opened while signed out (a tapped digest's Insights) stays through the sign-in. A Family member's page goes with the board, Family closes when the server has no board and Cycle when tracking is turned off; with sharing off, More stops listing Family but an open Family page stays and says so.

**Pages**, one bullet each, in the web's order: a page's own work edits only its bullet. Each page is its own file or folder, so building one changes only that.

- **Home** (`Dashboard/TodayScreen.swift`, `OrganicHome.swift`, `TodayCards.swift`, `Home/`):
  - **The header** (src/components/shell/ShellHeader.tsx and TopBar.tsx, as the web's phone shows them): "Hello," over your name and "Here's your health today." (or "on Friday, October 23."), your avatar, then the top bar: "Demo data · Connect yours" while demo data shows, the day with previous and next, Refresh (which syncs Apple Health and WHOOP) and Edit widgets (its words only on a phone wider than 420pt, as on the web). The iPhone's own sync line sits under it. Pull down to refresh too.
  - **Above the page:** "Your dashboard fills in once you connect…" while nothing is connected (App.tsx `noSources`), the one-time family note, and the summary's heads-ups (only the iPhone shows these).
  - **The figure** in your perspective (`settings.perspective`; servers before it read as the portrait): your cut-out photo with its ASCII reveal (skipped with Reduce Motion; while the photo can't be loaded, offline say, the digital human stands in and it's tried again after each load), the digital human (`DigitalMan`, also for a portrait not made yet, with the web's note on where portraits come from on this server), or no figure for "Just the statistics". Blood oxygen and heart on the left, breathing on the right, each dot green, amber or red against your usual (gold without a level) and moving at its own number; the heart's opens live heart rate. Labels are placed as the web places them (`Figure.tsx`), on a glass plate over the digital human in dark mode. Then "A clearer picture. A healthier you." and Your measurements, to Vitals.
  - **Cards, one to a row** as on the web's phone: resting heart rate, blood oxygen, HRV, sleep, recovery (WHOOP's only; VO₂ max is Body's) and respiratory rate in their washes (`Home/SignalCards.swift`, which Vitals and Sleep use compact); a tap opens the metric's sheet, and without a reading a card says "Connect a source to get started". Then Today's nutrition (the day from 6:00 to 21:00, from the food log, only with Nutrition on; its orb logs food) and Your health journal (today's latest check-in, held in memory only; hidden on a server without the journal, until a load finds one). Home reads the food totals and the check-in itself (`Home/HomeReads.swift`) and hands the cards what came. The day by hour (it opens the Day view) and the cycle's phase follow, as only the iPhone has them.
  - **Optional cards**, off until you turn them on in **Edit widgets** (or Profile → Cards): strain or active energy, activity, food totals (with Nutrition on), Today's timeline (scrub it and the figure's heart follows), the week so far and recent insights. Edit widgets is the web's sheet: "On this page" and "More you can add", each switch saved at once and put back if the server says no.
  - At every text size nothing runs off the screen or is cut short: the top bar, the family note, the sync line and Edit widgets' buttons wrap, the figure's labels stop growing at xxLarge (VoiceOver reads them in full), and the cards' feet stack.
  - **Ask McFly:** a pill above the tab bar, on Home only, opens Ask McFly under More (its bullet below). It shows whenever someone's signed in, as on the web, McFly off included: the page then says why in the web's words.
- **Family** (`Dashboard/FamilyScreen.swift`; under More, signed in with sharing on): everyone who shares, each against their own last 30 days, and a person's page over the board.
- **Vitals** (`Vitals/`): until it's built, Trends' Vitals charts over 7 days, 30 days, 90 days or a year. Drag across a chart to read a single day.
- **Body** (`Body/`): until it's built, Trends' Body and Activity charts as two tabs. Activity has steps against goal, plus workouts.
- **Cycle** (`Cycle/`, `Dashboard/CycleViews.swift`; only while cycle tracking is on): this cycle's phase ring and estimates, each fertile day's estimated chance, the temperature curve for any cycle (cover line, ovulation, the rise after it), a five-week calendar, past cycles split before and after ovulation, and patterns from your own cycles. Estimates never mark a day as safe.
- **Nutrition** (`Dashboard/NutritionScreen.swift`, `NutritionViews.swift`, `FoodLog*.swift`, `Nutrition/`): the web's page (`src/pages/Nutrition.tsx`, `NutritionChat.tsx`, `FoodLog.tsx`).
  - **Off:** what it shows and what stays private, and Turn on Nutrition, which asks first what you want to see (nothing chosen in advance). Nothing is read from Health or kept until then.
  - **Views:** a quiet row of words, as on the web: Today, Trends, Macros, Hydration and Log (no Macros or Hydration with "No amounts"). A link's `?tab=` opens one (`overview` is Trends's old name), and Home's orb (`compose=1`) opens Today with the composer ready. Each link applies once (`NutritionLink`), so coming back to the tab keeps the view chosen since.
  - **Today** (`Nutrition/NutritionToday.swift`, `NutritionChatModel.swift`): a conversation with McFly, beside the day it adds up to, for today or any day of the last year ("Viewing"). The day is `POST /api/nutrition/log/day`, so no date is in an address; a server without it shows the Log instead.
    - **Tell McFly** in your own words, with a photo, or by voice, and check its estimate in the conversation: rename an item, change how many or the time, leave things out, then save, or discard it. Nothing counts until you save. A message while an estimate is open corrects it, on its day and time, with its photo sent again (at most 1,000 characters, as the server takes). An estimate made on the web and still waiting joins the conversation to be checked.
    - **+** adds a photo (camera or Photos), searches foods or a barcode (and scans one where there's a camera), types amounts or adds water, all to the day viewed: now on today, midday on a past day.
    - **Voice notes** (`Nutrition/VoiceNote.swift`): hold the orb to talk (with VoiceOver, activate to start and again to stop), half a second to a minute. The words fill the composer and are never sent on their own. The recording is AAC in a temporary file for as long as it records, read into memory and deleted before it's sent once to `POST /api/ai/transcribe`; it's never kept. Leaving the page or the app going to the background ends a note, and anything that comes back for it is dropped (each note has its own number). Off, a press says why in the web's words.
    - **The line under the composer** says who reads an estimate and where your words and photos go (your own Claude, OpenAI or Gemini key, or healthOS's shared assistant), or what's missing for one, in the web's words, from the server's own flags.
    - **Your daily balance:** kcal (or meals, with "No amounts") in a ring of protein, carbs and fat by weight, in the web's soft colours, and fiber, sugar, sodium, alcohol and water underneath. **Your food journal:** the day's entries, each with Edit and Delete, and which app's totals count that day.
    - **Kept in memory only:** the conversation, its photos' small copies and the last full photo (for a correction) go with the page when you sign out, or someone else signs in, or another server.
  - **Trends:** Energy (only when calories are shown), Protein with a neutral week-on-week note, Water in glasses, Days logged, a macro balance donut with fiber, sugar, sodium and caffeine, and food insights worded as associations.
  - **Macros and Hydration** over 7, 30 or 90 days: the average day (each nutrient over the days it was logged), a chart per nutrient, and which app counts on days two logged; water and caffeine averages. Every chart also reads as a table.
  - **Log** (servers with the food log, `GET /api/nutrition/log`): one day at a time of the last two weeks, each entry with Edit and Delete, and Add food or drink: water in one tap, search, scan, McFly's estimate of a photo or words (reviewed before it's saved) and typed amounts, only what your "numbers" setting shows.
  - **Photos** are turned upright, shrunk on the phone to 1,280 px on the long edge and re-encoded, which drops the location and other metadata (`PhotoPipeline`), and are sent only for that estimate.
  - **Saved to Apple Health:** see Apple Health sync below.
  - **No judgement:** a day with nothing logged is a gap, never a zero. A target you set is a plain dashed line. No score, no "remaining", no red or green.
- **Journal** (`Journal/`): coming in this build. Its data (`Journal/JournalAPI.swift`) is the foundation's.
- **Sleep** (`Sleep/`): until it's built, Trends' Sleep charts: stacked stages, and sleep performance from WHOOP and sleep efficiency as separate cards, each hidden on its own.
- **Blood records** (`Labs/`): coming in this build. Its results' model, words and bar are in `Labs/LabsModel.swift`.
- **Ask McFly** (`Dashboard/McFly.swift`, `AI/`): under More, and from the pill at the bottom right of Home (McFly's orb, "Ask McFly", "A little more clarity"), which shows whenever you're signed in, as on the web. Signed out it asks for sign-in.
  - **The page:** the web's line and New chat, five questions to start with, then the conversation (`/api/mcfly/chat`, streamed). Every piece of data McFly reads is listed, the one it's on shimmering; its answers use the web's little Markdown (paragraphs, lists, bold; never a link), with its charts between them. Stop keeps what arrived. Beside Ask: the questions left today on the shared key, or "On your Claude key" on your own key, whose cap isn't counted down (reaching it says so).
  - **Where McFly can't answer** (no assistant on the server, or the admin turned it off): the reason in the web's words, and "Connect your own key" (the Chatbot sheet) where the server can store keys.
  - **Your own AI keys:** the Chatbot sheet (who answers Ask McFly: OpenAI, Claude or Gemini on your own key, or healthOS's shared Claude, with an optional model) and the OpenAI sheet (meal photos, descriptions, voice notes and portraits), which Profile opens. A key is sent once to `PUT /api/ai/keys/:provider`, for the server to check with its provider and store; the phone never keeps, caches or logs it, and shows only its last four characters. A refused key shows the server's own words. Where the server can't store keys, or predates them, each sheet says so in the web's words.
  - The conversation stays in memory only, and is forgotten on sign-out, another person's sign-in or another server; a question still on its way never lands in the next person's. A 401 from Ask McFly (the session ended elsewhere) brings up the sign-in screen at once, as any other 401 does.
  - **In the Simulator only**, for scripted screenshots, also where no assistant can answer: `-aiSheet chatbot` or `-aiSheet openai` opens that sheet once signed in, and `-mcflyPreview thread|streaming|own|ownlimit|limit|off` (with `-mcflyOpen YES` to open the page) puts a made-up conversation and status in memory.
- **Profile** (`SettingsScreen.swift`, `Profile/`): the web's Profile (`src/pages/Profile.tsx`), in its cards of rows, its words in `Profile/ProfileWords.swift` (`ProfileTests` checks them against the web's files):
  - **Your profile:** how you're shown and your age, with **Edit preferences** (the welcome's steps again, only where the status names `perspective`); **Chatbot** and **OpenAI · Nutrition & portraits**, which open the key sheets (`AI/`), as `profile?connect=chatbot` and `?connect=openai` do, once for each time the link is opened, Profile already up included (once the settings are in and `GET /api/ai` has answered, and never on a server that says it has no keys), and hide on a server older than own keys; **Account** (your email, Signed in, and **Change password**: current, new and confirm, the server's own words for a refusal; the server signs every other device out and sends this phone a new session, which it keeps; "This Mac, no sign-in" on a server without sign-in, and the email kept from the last status, with nothing to change, while the sign-in mode isn't known yet); **Connected sources** (Integrations); **Export your data**; **Privacy & data use** (the server's `privacy.html`); and **Sign out**.
  - **Export your data:** `GET /api/me/export`, downloaded straight into a file of its own under the app's temporary files (complete file protection), named as the server names it and handed to the share sheet. One at a time for the app (`ProfileExportJob`), so leaving Profile doesn't stop it or allow a second. Never in Documents or a cache, never logged, and deleted once the share sheet has gone (not when an activity in it is cancelled), before the next export, at launch, and the moment nobody's signed in, another server is set or someone else signs in, wherever the app is: the download stops and a share sheet still up goes with it. The server's own words for a refusal (once a minute), and the web's when nothing came or the download broke off: a broken download is never a short file.
  - **Your settings,** each row saying how it's set and opening its sheet (`SheetScaffold`), only where the status names its setting: **Units & daily goal** (name and goal save as it closes, and it won't swipe away while they're unsaved; units save at once; a goal outside 500 to 100,000, which the server would ignore, or too long to read, is refused here); **Cards** (a box per card by the web's pages, Optional marked, where this iPhone shows it, and **Show all** while a default card is hidden; a server older than optional cards gets only the 33 cards it knows and Show all clears its list); **Family board** (Share with family, and who with; signed in only); **Cycle tracking** (sex for health calculations, Track my cycle, your phase on your Family tile, deleting every cycle entry after asking); **Nutrition** (on only after choosing what you see, What you see, your targets, two to a row as the web's, saved as each field is left and as the sheet closes, which won't swipe away while one is typed and unsaved, deleting every food total after asking). Every change goes through `dashboard.save(settings:)`; no sheet stays up once nobody's signed in.
  - **Your age-group comparison** and **Your portrait photos** (`PeersSection`, `PortraitPhotosSection`), which open in place, in the web's order; "Use a photo as is" (`PhotoSection`) is inside the portrait photos, as below (`ProfileTests.testThePhotoPickerShowsOnce` checks it shows once).
  - **This iPhone,** in every phase so the server can be changed before sign-in: the server address and sign-in state, **Sync now**, the last sync, the ingest token and Test connection, Health access, background sync and the first upload's reach, the weekly digest reminder, the simulator's sample data, and **Upload all history again**.
- **Your age-group comparison and Your portrait photos** (`Peers/`, `Portraits/`): Profile's two cards that open in place, `PeersSection()` and `PortraitPhotosSection()`, shown only while signed in. What they read stays in memory and goes with a sign-out, another person's sign-in or another server. A failure reads as the web's does: the server's own words, or "Couldn't reach healthOS…" offline. VoiceOver hears what the web reads out as it happens (a refusal, a failed step, Use's steps, a portrait being made), and a pill's words shrink a little, then wrap, rather than being cut off.
  - **Age-group comparison** ("Private to you"; `GET /api/peers`, read each time it opens, after each load, and as soon as taking part or the age changes): where your 30-day average for each measurement and source sits among people your age who also take part. Only a quarter (never a rank), the group's rounded median and middle half, and its size as a range ("20+") ever come back, and you're never in your own group. The web's words for not taking part (with a link to Edit preferences), too few days of your own, a group still gathering, no readings, and the local preview's sample group. Hidden on a server whose settings don't name `peerComparison`, or that answers the read with its catch-all 404.
  - **Portrait studio:** up to five reference photos (from Photos or the camera, turned upright, shrunk to 1,600 px and re-encoded without metadata on the phone), kept private in your account. **Make my portrait** sends one to OpenAI, on your own key or the server's, one portrait at a time; the list is checked every 3.5 s until it's ready or failed. Tiles show ready, In use, being made or failed (with the server's reason). **Use this portrait** fetches it, cuts it out on the phone, saves it as your profile photo, marks it in use and sets "Your own portrait", in that order. Without a key to make one, it says why in the web's words (keys can't be stored on this server, or connect yours); the day's limit (10) and other refusals are the server's own words. The list is read again when the welcome closes (its first step adds reference photos) and when your own OpenAI key is connected or removed. Images are fetched into memory and shrunk there, never written to disk or the profile photo cache. A server older than portraits shows only Use a photo as is.
  - **Use a photo as is:** choose a photo, see the cut-out and avatar made on the phone, then **Save photo** (`POST /api/profile/photo/upload`) or Cancel. **Remove photo** (`POST /api/profile/photo/clear`) takes it off Home, Body, your avatar and the Family board, and drops the copies kept on the phone.
- **Integrations** (`Integrations/`): coming in this build.
- **Admin** (`Admin/`): the web dashboard's Admin page, shown in the app, until it's built here (`AdminScreen.native`).
- **Insights** (`Dashboard/InsightsScreen.swift`; only the iPhone has it): the weekly digest, patterns from your own history, two scatter plots and a year heatmap.
- **Day** (`Dashboard/DayScreen.swift`): one day by the hour, opened from Home.
- **Live heart rate** (`Live/`): opened from the heart callout.
- **Metric sheet** (`MetricSheet/`; over any page, from a card's arrow): the web's sheet (`GET /api/metric/:key`, all 17 metrics).
  - Its ranges; where the values came from; the window's average beside the card's status; a line, bars or the day by the hour, each with a table of every value (one line a cell, scrolling sideways when it's wider than the sheet); lowest, highest and latest; the server's sentence; "What this means" (bundled from `shared/metrics.ts`, its source opened in the app's browser); and "Open {Page}" unless that's the page under it. Home's activity cards say "Open Activity" and Body's own "Open Activity on Body", as the web's do.
  - An empty window moves to the longest range and says so, until you press a range yourself (the one already chosen too). Never measured, it says "No measurement yet." with Manage connections.
  - A server without the sheet, or without this metric's, gets one built on the phone from `GET /api/trends` and `GET /api/day`, without the parts only the server can say (the status, the sentence, the devices).
  - **Memory only:** the sheet's own answers go when it closes, and a sign-out closes it. Built on the phone, its trends and day reads share the Dashboard's in-memory caches with every page, which sign-out clears.
  - **Every text size:** everything grows with the text, the chart and table switch and Manage connections included, and nothing breaks a word; the range and switch buttons take taps over 44 by 44 points.
  - `MetricSheetTests` checks the bundled words and rules against the web's files; `MetricSheetSnapshotTests` and `MetricSheetLiveTests` draw its states when `TEST_RUNNER_METRIC_SHEET_SHOTS` is set.

Cards hide or switch to fit your sources, as on the web: no WHOOP means VO₂ max instead of recovery, active energy instead of strain, and HRV labelled SDNN.

**Sign-in:** the same account as the website. On servers with per-person accounts the app asks for email and password; older single-user servers need only the password. The app works with either.
- **The way in** (`Dashboard/SignInView.swift`, `JoinView.swift`, `Auth/`, `Onboarding/`) is the web's (`src/pages/Login.tsx`, `Onboarding.tsx`), full screen in its welcome frame with no tab bar: the healthOS mark, a glass card, the tagline. **Change server** at the top right is the iPhone's own; it opens Profile. A page opened from More while signed out asks for sign-in under its own Back and the tab bar.
  - **Sign-in:** "Sign in to healthOS", or on a brand-new server "Create your admin account", whose first sign-in makes the admin. The server's own words for a wrong password or too many tries.
  - **Invites:** **Have an invite code?** takes the code or the whole invite link. The link is checked first ("Checking your link…"); then name, email (locked when the invite is for one) and password, with what the Family board shows of you. No email is ever sent.
  - **Reset links:** the admin's link (`…/#/reset/…`) is pasted under **Have a reset link?** (only the iPhone has it: the web opens the link in the browser). A new password signs out every other session.
  - **The lockout:** a failed link check counts toward the same lockout as a wrong password, which a household on one network shares. So a code or link that can't be one (a letter a code never has, a code where a reset link goes) is turned down on the phone and never sent. A server older than the check, asked while signed out, answers 401: the form opens unchecked.
  - **The welcome** ("Make this space yours"): after any sign-in, while the server says a new account's onboarding isn't done (an invite's, or a brand-new server's owner), the web's three steps cover the app. A sign-in shows nothing of the dashboard until that person's own status is read, so a new account goes straight to its welcome. The steps: your perspective (your portrait, with the photo it's made from; the digital human; just the statistics), a little about you (how you describe yourself, your age, a card saying what Home and Body will show) and anonymous peer comparisons, unticked until you tick them and only with an adult age. Each step forward saves the steps it leaves, so the app resumes where you were; a step tab that jumps ahead saves what it skips, and stops on step 2 until there's an age. **Enter my workspace** finishes it and opens Home; **Sign out** is the only other way past it, as on the web (it waits while a step saves). Its steps show only on the signed-in person's own status. Profile's Edit preferences (`dashboard.open(.welcome)`) runs the same steps without touching onboarding and goes back to Profile. Only where the server's status names `perspective`.
  - **The portrait's reference photo** is turned upright, stripped of its metadata and shrunk on the phone (`PhotoPipeline.reference`), kept in memory only, and goes with a sign-out. Change keeps the new one before deleting the old; from the pick until it's kept, the row says it's saving and turns down another. The line under it says what this server can do (an OpenAI key or not), in the web's words.
- **Session:** the 30-day session cookie lives in the Keychain.
- **Sign out** (the account menu, or Profile) forgets what's on the phone of that person: the cached summary and loaded data, the Family board and its photos, the profile photo kept in Caches and Ask McFly's conversation. Then it's back to Home, with nothing open on any tab.
- **A session that ends without Sign out** (it ran out, or was ended on the web or by an admin): the next request's 401 brings the sign-in screen, and everything loaded for that person goes from memory as with Sign out, so the avatar, More and Ask McFly show nothing of theirs. Only the summary kept on disk stays, for their next launch.
- **Local servers:** one with no password set needs no sign-in.
- **A server whose sign-in isn't set up** (`/auth/me` says "misconfigured") says what the web's sign-in page says: sign-in isn't available right now, try again later. No server, the sign-in screen and this state are drawn by `PhaseGate` (`Shell/PhaseGate.swift`) on every page, from the sign-in screens' own files.
- **Time zone:** after each status read, if the server's `settings.timeZone` isn't this iPhone's, the app sends it (`PUT /api/settings {timeZone}`), as the web does, so the hosted server's "today" is yours. A zone is sent once per session: a server that keeps its own, or refuses it, isn't asked again, and one that couldn't be reached or failed (a 5xx) is asked on the next read.
- **Sign out pauses the Apple Health sync.** The ingest token belongs to one account, whoever is signed in, so the app remembers which account it was set under (or, for a token from an older build, the first account seen signed in). That record lives in the Keychain beside the token, so the two outlive a reinstall together.
  - **Sign out:** nothing is read or sent, in the app or in the background, until someone signs in; a sync already running stops before its next upload. The same account resumes the sync.
  - **A session that ran out or was ended elsewhere, or none at launch:** while the token's owner is known, the sync goes on, as it did before owners were kept. A token whose owner can't be told (pasted while signed out, or from an older build after a reinstall) waits for a sign-in, and the sign-in screen says that this iPhone's Apple Health uploads wait until you sign in.
  - **Someone else signs in,** or a new account from an invite: the token is removed and Profile asks to set this iPhone up again in Integrations, so a phone that changes hands never sends the new person's data to the last account once they sign in. The next token starts the upload from the beginning.
  - **The same account** is the same id on the same server, or the same id and email on a server reached at another address (a Mac server at home and on the LAN).
  - **A token from an older build** first seen while nobody is signed in is taken to be the email that build last signed in with here: that email signing in keeps it, any other removes it. With no email to go by (a reinstall), it can't be told whose, so the next sign-in removes it.
  - A token pasted while signed out is the next person's to sign in.
  - Servers without sign-in work as before, unless the token belongs to an account on another server: then a pause from Sign out stays until that server's account signs in.
- **Errors:** when the server refuses something with a message written for people (400, 403, 409, 413 or 429), the app shows that message as it is, as the web does; otherwise it says "Server answered" with the code. A sign-in, an invite, a password change, and an invite or reset link's check show theirs too, a used-up link's 404 included. A feature the server hasn't set up answers 503 in its own words ("Connecting your own key isn't set up on this server."), shown as they are.
- **Offline:** the last summary is cached on the phone, so the app opens with numbers even offline.
- **Fresh data without re-downloading:** the app checks `GET /api/version` on open, on return, after syncs and every minute while open. It downloads the summary and trends again only when the version changed or the day rolled over, or on pull to refresh. Servers without `/api/version` get a reload on open, on return and after syncs.

## Look

The app takes the web's look from `src/styles.css`, light and dark.

- **Tokens** (`Dashboard/Tokens.swift`): every colour, gradient, shadow and corner radius in the CSS's `:root` block and its dark block, by its CSS name. A token the dark block doesn't name keeps its light value. `Palette` (`Dashboard/Theme.swift`) names them for the views. `ThemeTests` reads `styles.css` and fails if a value here differs, or if the CSS gains a token the app doesn't have.
- **Cards:** the white glass sheen with a soft card shadow and a white edge, padded as the web's .card (20pt, 18 at the bottom); the metric washes (green, peach, pink, lavender, mint, slate, cream, blush, blue) are the CSS's own ellipses, strongest near the bottom, drawn over the sheen. Shadows are drawn as CSS draws them, spread included. A gradient (`GradientFill`) is drawn in slabs of at most 1,000 points, so a card of any height is filled whole: one Canvas past 8,192 pixels isn't drawn at all in a Form or List row.
- **Tint:** the forest accent. In dark mode, words take its text step (`--accent-text`), as on the web, since the dark accent reads under 3:1 as text. So the tint is for words and marks only, never a fill: a filled button is `.accentPill` (the accent gradient with white words, as the web's .btn-primary), and switches are the web's green (`AppSwitchStyle`, set at the root and in SheetScaffold), the system's own switch in the web's colour.
- **Forms and lists:** no page uses the system's Form any more. One that does sits on the web's page with its rows on its surface with `.appForm()` and `.appFormRows()` (`Components/AppForm.swift`), its words in the system's label colours: a foreground style set on a Form turns its headers, footers, values and text buttons all the one ink.
- **Avatar:** your photo, or your initial in sage on pale sage (`--accent-soft`), in a thin white ring with the pill's shadow, as the web's .avatar.
- **Font:** DM Sans, the web's face, for all text. It's bundled as `Fonts/DMSans-Variable.ttf` with its licence (`Fonts/OFL.txt`) and registered in `UIAppFonts`.
  - `Font.app(.footnote, weight: .medium)` and `Font.app(size: 11, weight: .medium, relativeTo: .caption2)` (`Dashboard/AppFont.swift`) pick a point on the font's wght axis and scale with Dynamic Type, also when the text size changes while the app is open. `Font.app(fixedSize:)` is for text drawn to fit a shape, such as an avatar's initial. Views use these, never the system text styles.
  - Text without its own font (Form rows, fields) takes the app's default, `Font.app(.body)`. Bar titles, tab labels and segmented pickers are UIKit's, and are set at launch (`AppFont.styleBars()`). Bar titles follow the text size. Tab labels and segmented pickers stay at one size, as the system's do: their bars don't grow, so a scaled font would be cut off. The tab bar takes its font only from a `UITabBarAppearance`; UITabBarItem's own appearance is ignored.
  - Some system views set their own system fonts, whatever the app's. The app has its own version of each: `Unavailable` (`Components/Unavailable.swift`) for ContentUnavailableView's empty and error states, `ChartLegend` for a chart's legend, and `Font.axis` on every `AxisValueLabel`: DM Sans at 11pt whatever the text size, as the web's `.axis-label`, so the ticks never pile up or run off a card at the largest sizes (VoiceOver reads a chart's values).
  - SF Symbols keep the system font, so their weights match. Alerts, confirmation dialogs and date pickers stay in the system face too, since the system draws them. Toolbar buttons ("Done", "Save") take the app font on iOS 27, where SwiftUI draws them. Two lines are marked "system face" in their comments: the cycle ring's ○ and ● (not in the latin set) and the reveal's monospaced characters.
  - `AppFontTests` reads the app's sources and fails on a system text style or `.system(` font outside those cases, a ContentUnavailableView, a legend that isn't `ChartLegend`, an axis label without `Font.axis`, or a `.borderedProminent` button.
  - It's the web's latin subset: other scripts fall back to the system face. It has no tabular figures, so digits are proportional, as on the web, and `.monospacedDigit()` doesn't change them. The web's own file (`@fontsource-variable/dm-sans`) has none either, so its `font-variant-numeric: tabular-nums` changes nothing there.
- **Shared pieces** (`Components/`): the accent and quiet pill buttons (the quiet pill's words wrap at the accessibility sizes, in a box with the pill's rounded corners), Badge, ChoiceCard (radio card, its mark the web's radio in light and dark), ChipToggle, Eyebrow, PageIntro, SheetScaffold (eyebrow, title, close button, its buttons after the body on the right with no band of their own, the sheet gradient, full height, scrolling as one, as on the web: with the keyboard up, its buttons scroll up above it like the rest), ProfileCard and ProfileRow, Collapsible, Orb (McFly's mark; its pulse stops with Reduce Motion), RowIcon (a row's icon, which stops growing at xxLarge in a column that grows with it), the "—" empty value, Unavailable (empty and error states), ChartLegend, and SafariView. Translucent fills turn solid with Reduce Transparency.
- **The largest text sizes:** at the accessibility sizes, Home's metric cards go one to a row, the chart pages put their range picker under the page's line, and More puts each icon over its page's name, so no word breaks in the middle (a one-word name shrinks a little first, `wholeWords`). The pills over the figure stop growing at xxLarge, as the labels beside it already do; VoiceOver reads them in full.

## Building a page

What every page uses, so each page's work stays in its own files.

- **What the server can do** (`Shell/Availability.swift`, `dashboard.availability`): own AI keys (`GET /api/ai`), meal estimates and voice notes (the food log's `can`), portraits (`PortraitList.canGenerate`), reading lab reports (`GET /api/labs/reader`) and Ask McFly (its status, McFlyChat's). Each flag is the server's own answer, never an assumption about a server, since keys come and go.
  - A flag is nil until the server says, and nothing is shown about it until then: never "not on this server" because a read failed.
  - The shell reads `GET /api/ai` after every load while signed in. A page that needs it sooner calls `dashboard.loadAI()`, and one that gets an AiStatus back (saving a key) passes it to `availability.heard(ai:)`. Each newer AiStatus also brings the food log's estimate and voice flags up to date, as the server works them out from it, so a key connected or removed shows on Nutrition at once.
  - The web's own sentences for a feature that isn't there are `ServerWords`, quoted from the web files they're in (a test checks them).
  - It's forgotten with a sign-out, another person's sign-in or another server, and never kept on disk.
- **Older servers:** "Change server" can point the phone at an older Mac or LAN server. A route it doesn't have answers its catch-all 404 `{"error": "Not found"}` (or, older still, a 404 with no JSON): `APIError.routeMissing`. `APIClient.optional` (a GET) and its write form (`POST /nutrition/log/day`) return nil then, so the page hides or falls back. A route's own 404s ("No such entry") aren't that. A route for one item by id (an image) answers the same "Not found" when that item is gone, so use it only on routes that answer a list or a state.
- **Settings:** `dashboard.save(settings:)` (`PUT /api/settings`) shows the status the server answers with and keeps it with today's summary; `reload: true` reads the summary again after units, name, step goal or demo data change. An older server ignores keys it doesn't know and still answers, so a feature shows only where the status names its setting (onboarding only where `settings.perspective` is present), never because the save went through. Another write that answers with the status goes through `dashboard.showChanged(_:)`. An answer that lands after a Sign out, a 401, going offline, someone else's sign-in or another server shows nothing and throws `CancellationError`, for the caller to stay quiet about; `changeCards` and `followTimeZone` do the same.
- **One person's reads:** a read whose answer only means something for the person who asked goes through `dashboard.fetchForThisSession { … }`: GET /api/ai and the lab reader, every portrait call, and the food log and its day (`loadFoodLog`, `loadFoodLogDay`), whose `can` feeds `availability`. An answer that lands for another session (a Sign out, a 401, someone else's sign-in, another server) throws `CancellationError`, and a 401 for the last person's request never signs out whoever signed in since.
- **Endpoints:** each page adds its own as an `APIClient` extension in its own folder (`Portraits/PortraitsAPI.swift`), with `request` (a raw body takes its `contentType` and extra `headers`, such as X-Filename), `get`, `sendJSON` and `optional`. An upload that shows progress, or a download read as it arrives, builds its request with `urlRequest` and checks the answer with `checked`, on `APIClient.session`. Tests can answer in the server's place with URLProtocol classes, `APIClient.answering(with:)`; the app never calls it.
- **Cards:** where each card shows (`CardPlace`: a page, and its tab) is in its page's own table: `Home/HomeCards.swift`, `Sleep/SleepCards.swift`, `Body/BodyCards.swift` and `Nutrition/NutritionCards.swift`. Profile → Cards says "Home", "Sleep", "Body · Activity" or "Nutrition · Overview" from it, and a card in no table changes the web dashboard only. `CardPlacesTests` has a test per page.
- **Photos** (`Photos/PhotoPipeline.swift`): a photo from Photos, the camera or a file is turned upright first, since the server never turns one (it reads the JPEG's own pixels). Then it's shrunk and re-encoded as a JPEG with no metadata: no location, time or camera. `PhotoPipeline.reference` shrinks a portrait reference as the web does: 1,600 px on the long side, then a quarter smaller each time until it's under the server's 4.4 million base64 characters. `addReference` (`Portraits/PortraitsAPI.swift`) sends it.
- **Over the app** (the shell presents them, so any page can ask):
  - `dashboard.showMetric(.hrv, page: .vitals)`: a metric's detail sheet (`MetricRequest`: key, section, the card's page for "Open {Page}", range, date), drawn by `MetricSheetView(request:)` (`MetricSheet/`). `MetricCard(..., metric:)` opens it from a card.
  - The welcome (`dashboard.onboarding`, `Shell/Welcome.swift`): full screen whenever the server says a new account's onboarding isn't done, after any sign-in, and for `open(.welcome)` (Profile's Edit preferences), drawn by `OnboardingView(mode:)` (`Onboarding/`). Only signed in, and only where the status names `perspective`.
  - Ask McFly on Home: the shell mounts `AskMcFlyEntry` (`Dashboard/McFly.swift`) in every phase; it decides whether it shows and what a tap opens.
  - Sheets other pages present: `ChatbotSheet` and `OpenAIKeySheet` (`AI/`, Profile's key rows and `?connect=`), and `FitbitImportSheet` (`FitbitImport/`, from Integrations).
- **Tests:** a page's tests are in a file of its own, so a page's changes edit only its file: `FamilyTests` (the Family board), `HomeFigureTests` (Home's figure, Today's path and grid), `NutritionScreenTests` (Nutrition), `ProfileTargetsTests` (Profile's targets). The shell's and the shared models' are `ShellTests`, `SharedModelsTests`, `SharedTypesTests` (which fails to compile if a shared piece goes private again) and the rest.
- **Shared reads and constants** (decoded once, so two pages never define the same type):
  - The journal (`Journal/JournalAPI.swift`): `dashboard.journal(days:)` (nil on a server without it), add, change and delete, `JournalEntry`, `JournalData` and the web's five moods. Home's card and the Journal page both use it.
  - Lab results (`Labs/LabsModel.swift`): `dashboard.labs()`, `LabsData` and its markers and panels, the web's words for a result against its range (`LabWords`), and its bar (`LabRangeBar`), for Blood records and Body's Key biomarkers card.
  - Cycle days carry each source's part (`CycleLogDay`: `apple` and `manual`), for the log sheet; a day's fields read as before.
  - `dashboard.deletePortrait(id:)` beside `addReference` (`Portraits/PortraitsAPI.swift`).
  - Ports of the web's `shared/` constants in `Shared/`: `Peers` (the minimums, age groups, measurement pairs and quarters, from `shared/peers.ts`), `Perspective` (portrait, digital or stats, read from `settings.perspective` for the welcome, Home and Profile; `Settings.perspective` stays the server's string, so a value this build doesn't know still counts as named) and `FigureVariant.of(settings)` (the digital human: the one chosen, else by gender, else the man; `.drawn` is the man until the woman's artwork exists). Their tests read the web's files.
  - The art: `DigitalMan` and `JournalGut` in Assets.xcassets, the web's `figures/digital-man.webp` and `journal-gut.webp` as PNGs.
  - The chart pages' controls (`Components/ChartPageControls.swift`): `RangeFilters` (7 days to a year, and Day), bound to `dashboard.rangeDays` so the range follows from page to page, `PageTabs` and `DayNav`.
- **Permissions:** the camera's purpose covers meals, barcodes, portrait reference photos and paper lab reports, and names no provider; the microphone's is for voice notes (`project.yml`, which writes `Info.plist`).
- **Shared views:**
  - `CameraPicker` and `BarcodeScanner` (`Components/`).
  - `PhotoSection` and `PhotoPreview`, "Use a photo as is" (`Portraits/PhotoSection.swift`).
  - `HoursChart` (a day by hour), `WorkoutsCard` and `WorkoutListRow`, `TrendsLoader` and `MetricCard`.

## Apple Health sync

- **Reads** steps, active energy, exercise minutes, walking + running distance, heart rate, resting HR, HRV (SDNN), blood oxygen, respiratory rate, sleeping wrist temperature, body temperature, weight, body fat, lean mass, VO₂ max, sleep stages, mindful sessions and workouts.
- **Finds what changed** with one HealthKit anchored query per type. Only the local days touched by new samples are re-read.
- **Aggregates on the phone** into the same per-day rows as `server/apple/import.ts`:
  - Sum metrics keep the best single source per day.
  - Steps WHOOP writes into Health compete too (iPhone, Watch or WHOOP; the highest total wins, never the sum), and the hours follow the winner. WHOOP's other records stay skipped, because healthOS reads WHOOP's API.
  - Sleep counts toward the wake day (6 h rollover). Overlapping segments are merged, and the source with the most sleep wins.
  - Each night's stages also go up as a timeline (`sleepStages`) for the Sleep page: one stage at a time, the main sleep only (a same-day nap counts in the totals but isn't drawn), from the source that won the night. A night with no sleep is sent empty, which clears it, but only when the window had any sleep at all, so a phone without sleep access never erases nights from an export import. The first sync with a server that stores stages sends the last month again once, so recent nights have them; older nights get theirs with "Upload all history".
  - Days use each record's own time zone (`HKMetadataKeyTimeZone`, or the device's).
- **Uploads** a week of days per request to `POST /api/apple/ingest` with the bearer token, newest week first. A day whose upload fails stays queued for the next sync. Nothing goes up after Sign out, or while signed out with a token whose owner isn't known (see Sign-in above).
  - Every sync sends today, plus any changed day in the last 30.
  - Older days (the first upload, or the one-time hourly backfill) wait in a saved queue. They go up newest first, four weeks per pass, only while the app is open and not in Low Power Mode. Profile shows how many are left.
- **Cycle tracking:** menstrual flow, spotting, ovulation tests, cervical mucus, sexual activity, basal body temperature and Health's cycle symptoms (cramps, bloating, headache and the rest; one logged as "not present" is left out). The app reads these only after you turn cycle tracking on in healthOS settings and the server answers that it stores cycle days. Each day sent replaces that day on the server.
- **Nutrition** (food totals from the apps you log meals in): energy, protein, carbs, fat, fiber, sugar, saturated fat, sodium and alcoholic drinks.
  - **Off by default.** The app reads, asks Health about and watches these types only while the server's ingest reply says you turned Nutrition on (`nutritionOn`) and lists the nutrients it takes (`nutrients`). Off, it reads none of them.
  - **Turning it on:** the sync that hears it asks Health about the food types and then reads their whole history. Turning it off forgets where reading stopped, so turning it on again sends the history again.
  - **Per app, never summed:** each day goes up as each app's own totals, and the server shows one app a day, because apps copy each other's logs through Health. A meal saved as a Food correlation counts once. Each day sent replaces that day.
  - **Deletions:** a food sample deleted in Health re-sends the last month, and a day left with no food goes up as `apps: []`, which clears it. An empty day is never sent otherwise: Health reads as empty when food access is off.
  - **Late writes:** food apps often write late, so the last three days are read again on every sync. Food energy alone wakes the app in the background.
  - **Values the server would refuse stay on the phone:** a total above its cap (a unit mix-up) is left out, so one bad log can't block a sync. Caffeine and water stay daily metrics, as before.
- **Food logged on this iPhone is written to Health** (`FoodHealth.swift`), so other apps see it. Only saved entries made here are written, never ones from the web or McFly drafts still waiting for review.
  - **One Food correlation per entry** (water included), plus a separate alcoholic-drinks sample, which a correlation can't hold. Every object carries `HKMetadataKeyFoodType`, `HKMetadataKeySyncIdentifier` `healthos.food.<entry id>` and `HKMetadataKeySyncVersion`, so a changed entry replaces its copy, and `HealthOSFoodLogEntry` = the entry id, which queries can leave out.
  - **Only the amounts you see:** with "No calories" no energy is written; with "No amounts" nothing is, and copies already written are removed.
  - **Asked once, when you save your first entry** (after the Add sheet closes), not at launch. From then on every Health request includes the food write types: on iOS 27 a request that leaves them out resets them.
  - **Reconciled** when Nutrition opens and after each sync, against the last 7 days of the log: changed entries are rewritten, deleted ones (here or on the web) removed. `food-health.json` in Application Support remembers what was written.
  - **Never counted twice:** the server already has the log itself. The water, caffeine and food queries leave out `HealthOSFoodLogEntry` with a NOT predicate, and adding up skips anything marked as ours again (key or `healthos.food.` sync identifier). Our own rewrites and removals don't count as changes either, so an edit never re-sends or clears a month of food.
- **Sleeping wrist temperature** counts toward the morning the night ends, like sleep, so it lines up with WHOOP's skin temperature for the cycle engine. Builds before this dated it by the evening the night began: the first sync after updating reads its history again once and re-sends every day it moved from or to, and the server drops a wrist reading from any day sent without one.
- **Syncs in the background:**
  - **HealthKit wakes:** an `HKObserverQuery` per type plus `enableBackgroundDelivery`. Wakes are hourly for heart rate, steps, energy, distance, exercise and breathing, and immediate for everything else.
  - **Backstop:** a `BGAppRefreshTask` (`health.mcfly.sync.refresh`).
  - **On a wake:** the app pushes changed recent days, then sends `POST /api/sync` so the server refreshes WHOOP, at most every 15 minutes.
  - **Skipped in Low Power Mode.** Health data also can't be read while the phone is locked.

Workouts and mindful sessions are keyed by their HealthKit UUID. If an earlier `export.zip` import holds the same one (same start instant and type), the server replaces the imported copy, so nothing is duplicated.

## Server setup

The app pushes to `https://health.mcfly.bot/api/apple/ingest` by default. Set the shared secret on the server, as a Vercel environment variable or in `.env` locally:

```bash
HEALTHOS_INGEST_TOKEN=paste-the-output-of-openssl-rand-hex-24
```

Without it, the endpoint answers 503 and accepts nothing.

## Install on your iPhone

Needs iOS 17 or later. Built and tested with Xcode 27. Bundle ID `health.mcfly.sync`, team `92X9CP6C6D`.

1. Install the latest build from **TestFlight**. In App Store Connect → TestFlight, add yourself to an internal testing group once; new builds then appear in the TestFlight app. For a quick local install instead, run the `HealthOSSync` scheme on your phone from Xcode.
2. Open the app and sign in, or join with an invite code. It already points at `https://health.mcfly.bot`.
3. In **Profile** (More → Profile, or your avatar), paste your ingest token, then tap **Test connection**. Each person gets their own on the dashboard under Integrations → Apple Watch / Health → Set up the iPhone app; the owner can also use the `HEALTHOS_INGEST_TOKEN` value set on Vercel.
4. Tap **Sync now**. When the Health sheet asks how much history to share, pick **All Recorded Data** if you want a full backfill. The **First upload covers** setting can limit it further.
5. For background sync, leave **Background App Refresh** on for the app (Settings → General).

### Shipping a new TestFlight build

```bash
ios/testflight.sh
```

The script bumps the build number in `project.yml`, archives a Release build, and uploads it with the Apple account signed in to Xcode. Apple then processes the build, usually in 5–30 minutes, before it shows up in TestFlight. Change `MARKETING_VERSION` in `project.yml` for a new version number.

### Syncing to a Mac instead

To keep data on your Mac, run the server there with `HEALTHOS_LAN=1` as well as the token. It logs a LAN address such as `http://192.168.1.20:8788`, which you enter in the app instead. That port serves only the ingest endpoint. The phone must be on the same network, and iOS asks once for Local Network access.

## Simulator

Simulator builds have an extra **Add sample Health data** button. It writes two weeks of plausible data into the simulator's Health store, so the whole flow can be tried without a phone. Device builds ask for write access only for the food you log in the app. The live barcode scanner needs a real camera, so in the simulator type the barcode's number instead.

**Point the simulator only at a scratch server.** Whatever is in its Health store is uploaded as real Apple Health data. Never use the hosted site. Avoid `localhost:8787` too: with `DATABASE_URL` in `.env.local`, that server writes to the hosted database. Simulator builds start with no server address for this reason. The simulator shares the Mac's network, so a scratch server on the Mac is reachable at localhost:

```bash
env -u DATABASE_URL HEALTHOS_DATA_DIR=/tmp/healthos-scratch PORT=8790 HEALTHOS_INGEST_TOKEN=any-test-token-16chars node server/index.ts
```

Then enter `http://localhost:8790` and that token in the app's Profile.

Build and test from the terminal:

```bash
xcodebuild -project ios/HealthOSSync.xcodeproj -scheme HealthOSSync -destination 'platform=iOS Simulator,name=iPhone 18 Pro' test
```

For scripted runs, `xcrun simctl launch booted health.mcfly.sync -healthosToken <token>` sets the token (simulator builds only), as if pasted while signed out: whoever signs in next is its owner.

## Project file

`HealthOSSync.xcodeproj` is generated from `project.yml`. After adding files or changing settings, run `xcodegen generate` (`brew install xcodegen`).

## Known limits

- Deleted workouts and mindful sessions are removed on the server too. For other deleted samples, the app re-checks the last 30 days of daily values; for older edits, use **Upload all history again**.
- If every sample of a metric on a day is deleted, the server keeps the old value: a sync only adds and updates.
- Types you don't allow in the Health sheet read as empty. Those metrics just stop updating, and earlier values stay.
